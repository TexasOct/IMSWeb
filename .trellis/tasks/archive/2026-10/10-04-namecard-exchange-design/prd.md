# 名片交换功能拓展设计

## Goal

为 IMSWeb 设计一种补充实体名片交换的数字交换形式，减轻印刷工期、携带数量、损坏丢失、分类整理和复刻成本问题。完整规划资料上传与审核、账号绑定、分享收录、线上及线下交换、名片册、特殊展示和创作标签，不以完全替代实体交换习惯为目的。

本轮交付规划文档及研究证据。用户已同意建任务和开始完整规划；产品代码、数据库迁移、设备构建和上线需要在设计评审后另行进入实施。

## 背景与当前证据

- `fudaba_cards` 已统一现有名片来源，注册名片已有 owner、编辑审核、认领与图片存储；旧 `cards` 仍被历史认领读取。出处：`apps/api/migrations/postgresql/20260819000000_namecard_unification_foundation.sql:18`、`apps/api/src/infra/db/repositories/fudaba-repository.ts:3287`。
- 当前删除会清理图片，收藏读取当前公开卡片；已有 office-bound exchange request 数据基础，但没有挂载的完成交易/持有账本流程。出处：`apps/api/src/domains/community/fudaba/cards/handlers/delete-card.ts:35`、`apps/api/src/domains/community/fudaba/directory/handlers/list-favorite-cards.ts:12`、`apps/api/migrations/postgresql/0022_fudaba_domain.sql:174`。
- 担当搜索目前缺少本提案需要的角色资格分类；账号注销自动解绑尚未实现。出处：`apps/web/app/components/community/idol-multi-select.tsx:45`、`docs/architecture/platform-account-security.md:43`。
- 全站 UI 运行时固定中文，静态资源包含英文；没有可直接使用的名片创作 tag 池/管理归并/i18n。出处：`apps/web/app/i18n/config.ts:8`、`apps/web/app/i18n/provider.tsx:10`、[标签研究](./research/tag-pool-and-i18n.md)。
- Apple 已开放 Core Bluetooth central/peripheral 与 GATT；普通前台 BLE 需要用户蓝牙授权，不以 MFi 或受限 NFC 卡模拟资格为前置。Google Nearby Connections 官方支持 iOS/Android 互通，但有额外传输与权限成本；详见 [近场与权限研究](./research/proximity-exchange-and-permissions.md)。文档能力不代表本项目已有双机验证。
- 完整现状、源码与已有测试锚点见 [current-capabilities.md](./research/current-capabilities.md) 和 [source-map.md](./research/source-map.md)。读取测试不代表本轮重新执行通过。

## 原始需求清单

| ID | 用户要求 |
| --- | --- |
| NC-01 | 制作人名必填；可填只包含假名和英文字母的读法，作为排序辅助。 |
| NC-02 | 担当必填且仅表达名片展示角色；支持检索选择、未匹配的「其他」及管理员补候选。 |
| NC-03 | 角色范围为各子品牌可培育偶像及对手、事务员、社长；排除联动、剧中剧、愚人节角色。 |
| NC-04 | 支持企划输入；组合检索展开偶像，不能直接保存组合名作为担当。 |
| NC-05 | 所属团体选填，先考察象征性文本与筛选能力，社团功能联动作为待设计选项。 |
| NC-06 | 创作人员选填，支持设计师/画师的本站账号关联或外部主页。 |
| NC-07 | AI 标记由上传者自愿选择，不能因「疑似 AI」退回。 |
| NC-08 | 保存上传日期、所属账号；新上传默认绑定上传者，用户不能随意改所属账号。 |
| NC-09 | 区分待认领、待审核、未通过、已锁定及审核通过状态；有正常和隐藏显示状态。 |
| NC-10 | 至少上传一张正面图；背面方向默认跟随正面，按比例识别方向，编辑窗口允许旋转。 |
| NC-11 | 限制图片格式和大小，以不超过 1 MB 为用户提案示例；正面用于册和墙默认预览。 |
| NC-12 | 填写基础信息后提交审核；退回后修改重提；严重违规锁定且禁止编辑。 |
| NC-13 | 退回理由覆盖信息缺失、信息不符、重复上传、非企划、NSFW、侮辱现实人物；锁定后保留期与清理需设计。 |
| NC-14 | 支持编辑并重新审核，管理员可比较前后差异并识别细微改动。 |
| NC-15 | 个人名片可调整排序，设置快速交换单张或一组，隐藏名片不出现在本人以外的主页或墙。 |
| NC-16 | 删除仅解除绑定；名片实体和他人已交换收藏保留。 |
| NC-17 | 链接、二维码分享和 OGP；与现有社交分享基座衔接。 |
| NC-18 | 接收者可选择以自己的名片交换或单纯加入名片册；默认手动审批，可显式开启自动同意并在首次交换引导。 |
| NC-19 | 名片墙、个人主页和分享页使用同一申请规则；己方/对方已持有角标，禁止重复交换。 |
| NC-20 | 一对一进入交换界面、匹配对象、选择名片，双方滑动确认；预填快速交换名片。 |
| NC-21 | 考察 BLE 近场通信以应对差通信环境；同时评估 NFC 和红外可用性及降级入口。 |
| NC-22 | 失败交换在本地留下时间、对象、所选名片、交换方式等记录，任一方可重发并由服务器重新验证。 |
| NC-23 | 临时频道多对多交换，支持主发起人的二维码或相同四位数字加入；范围与有效期需设计。 |
| NC-24 | 后台静默交换模拟擦肩通信，双方显式启用时自动发送接收；需验证平台可实现边界。 |
| NC-25 | 名片册默认交换时间排序，支持制作人名/读法首字母排序，英文开头项优先。 |
| NC-26 | 名片册按企划、偶像、组合、所属团体筛选，可选择包含越境和多担。 |
| NC-27 | 用户可隐藏册中指定名片，默认不展示，专门启用显示隐藏才可见；不提供自定义名片册。 |
| NC-28 | 历史名片支持自助认领与补充资料；新名片默认绑定上传者，账号注销自动解绑。 |
| NC-29 | 未绑定不可交换；认领期后不展示、不检索、不计统计，但既有收藏可见。 |
| NC-30 | 固定比例展示容器，异型名片完整 contain 展示，支持非标准尺寸。 |
| NC-31 | 特殊工艺探索额外 Alpha 图层及预设效果，并说明视觉还原局限。 |
| NC-32 | 多页名片可额外上传内页、拖拽或编号排序，完整收录；数量及资源边界需明确。 |
| NC-33 | 机关名片无法由平面完整表达；评估模型和贴图的门槛及替代展示。 |
| NC-34 | 名片创作支持用户自定义 tag；用户输入形成共享 tag 池；管理端可合并同类项，并支持 tag 的 i18n。 |

### 本次调研补充的近场约束

- NC-20/NC-21：现场交换须考虑 iOS 与 Android 互通，体验参照 NameDrop 的对象预览和双方确认；优先省去手动加入 Wi-Fi、切换热点及进入系统配对设置，不因此禁止使用各自已有网络。
- 前台 BLE 为推荐路线：双方安装 App 并打开交换页，首次权限由系统授权；新增权限只在启用近场功能时请求，拒绝或硬件不支持时保留二维码/线上入口和所选名单。二维码入口需要网络，不能冒充完全离线完成。
- 多人环境必须能核对和选择对象；不能凭蓝牙信号最强自动交换，不能承诺厘米级或手机顶部接触检测。动画、震动与交换成功状态须有真实握手/回执依据。
- NC-22/NC-24：完全离线与后台静默保持独立阶段和验收。无服务器完成回执时只显示待同步或草稿；普通蓝牙授权不代表常驻后台能力，iOS 26 Live Activity 的可见会话另作专项评估。
