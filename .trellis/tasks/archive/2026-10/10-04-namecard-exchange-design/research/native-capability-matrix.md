# Native capability feasibility

Reviewed 2026-10-04; proximity and permission addendum checked 2026-10-06. Research only; no hardware tests. Platform facts below come from official documentation; protocol requirements are proposed design constraints. The [focused addendum](./proximity-exchange-and-permissions.md) owns the cross-platform foreground recommendation, Apple eligibility, first-use flow and current background-version qualifications.

## Existing shell

Inspected `apps/web/src-tauri/Cargo.toml`, `src/lib.rs`, all five `capabilities/*.json`, and `app/lib/native-glass.ts`. Cargo declares Tauri `2.11.3` (a dependency constraint, not proof of resolved version). Registered plugins cover filesystem, dialogs, deep links, opener, geolocation, native glass, iOS native images, and debug logging. Capabilities grant these functions; there is no BLE/NFC plugin or permission. The existing `invoke("plugin:native-glass|...")` bridge demonstrates the integration pattern. [Tauri mobile plugins](https://v2.tauri.app/develop/plugins/develop-mobile/) support Swift/Kotlin; suspended WebViews require native lifecycle handling and persistent receipts.

## Candidate matrix

| Combination | Assessment and constraints |
| --- | --- |
| Browser to browser BLE | Cannot promise: [Web Bluetooth](https://bluetooth.spec.whatwg.org/) exposes central/client access, not peripheral advertising/GATT hosting. [MDN](https://developer.mozilla.org/en-US/docs/Web/API/Web_Bluetooth_API) requires HTTPS, permission and user activation; browser availability must be detected. |
| Supported browser to foreground native app | Conditional central-to-native-GATT candidate; no universal mobile-browser or background guarantee. |
| Foreground iOS/iOS, Android/Android, iOS/Android | Recommended native prototype: common service discovery and GATT token exchange, at least one central and one peripheral. [Android advertising](https://developer.android.com/reference/android/bluetooth/le/BluetoothLeAdvertiser) and [GATT server](https://developer.android.com/reference/android/bluetooth/BluetoothManager) require hardware checks. No manual network join is required by this design; absence of bonding dialogs must be physically verified. RSSI is not centimeter-level targeting or proof of consent. |
| Traditional background iOS/iOS | Conditional, best effort under the [Apple background guide](https://developer.apple.com/library/archive/documentation/NetworkingInternetWeb/Conceptual/CoreBluetooth_concepts/CoreBluetoothBackgroundProcessingForIOSApps/PerformingTasksWhileYourAppIsInTheBackground.html): duplicate discoveries coalesce, scans slow, advertising frequency falls, names disappear and UUIDs enter iOS-only overflow. Wake work is approximately ten seconds. Restoration preserves selected operations, not continuous execution. This row is not an exhaustive account of newer Live Activity support. |
| Traditional background iOS/Android | Cannot promise symmetric discovery: Android cannot discover iOS overflow service UUIDs in this mode. iOS scanning Android advertisements is a conditional direction worth testing. |
| iOS 26 Live Activity background session | [Current Core Bluetooth](https://developer.apple.com/documentation/corebluetooth) documents continuing certain foreground privileges when a CBManager exists and a Live Activity starts before backgrounding. Treat as a visible, explicitly started session requiring separate radio/lifecycle tests; not proof of Android discovery, indefinite operation or force-quit/reboot recovery. |
| Background Android/Android | Conditional: [filtered PendingIntent scans](https://developer.android.com/develop/connectivity/bluetooth/ble/background) can wake a dead process; killed processes lose connections. Long operations need a `connectedDevice` foreground service started while visible or under an allowed exemption; Android 12+ restricts background starts. [Doze](https://developer.android.com/training/monitoring-device-state/doze-standby) delays CPU/network/jobs, so reconciliation cannot be immediate. |
| NFC invitation/tag reading | [Apple background NFC](https://developer.apple.com/documentation/corenfc/adding-support-for-background-tag-reading) on iPhone XS+ delivers tags after notification tap/unlock, with Wallet/camera/airplane-mode restrictions. Foreground Core NFC uses reader sessions and device checks. [Android Beam](https://developer.android.com/about/versions/10/behavior-changes-all#nfc) was deprecated in Android 10. [W3C Web NFC](https://w3c-cg.github.io/web-nfc/) covers NDEF tags, excludes peer-to-peer/HCE; [MDN](https://developer.mozilla.org/en-US/docs/Web/API/Web_NFC_API) supplies no universal-browser guarantee. |
| iPhone NFC reader / Android HCE | ISO7816 APDU prototype candidate with asymmetric roles and visible iOS reader UI, derived from [Apple tag API](https://developer.apple.com/documentation/corenfc/nfciso7816tag) and [Android HCE](https://developer.android.com/develop/connectivity/nfc/hce). No device result or generic iPhone/iPhone support claimed; restricted iOS card emulation is a different capability. |
| Google Nearby Connections | [Officially Android/iOS interoperable](https://developers.google.com/nearby/?hl=en), with Bluetooth/BLE/Wi-Fi internally. [Current Swift setup](https://developers.google.com/nearby/connections/swift/get-started?hl=en) includes Bluetooth, local network/Bonjour and location usage for high-speed hotspot connections. Alternative rather than default pure-BLE implementation. |
| UWB / Wi-Fi Aware / Apple proximity content sharing | Separate enhancements or integrations, not established universal Android/iOS NameDrop replacements. See the addendum for hardware/token, first-pairing and Apple-only sharing qualifications; no implicit transport fallback. |
| Infrared | Reject as cross-platform baseline: [Android ConsumerIrManager](https://developer.android.com/reference/android/hardware/ConsumerIrManager) requires optional emitter hardware and exposes transmission, not a reciprocal receiver protocol. No supported iOS counterpart was established. |

## Permissions and token protocol

[Android permissions](https://developer.android.com/develop/connectivity/bluetooth/bt-permissions): Android 12+ needs runtime `BLUETOOTH_SCAN`, `ADVERTISE`, `CONNECT` according to roles; older scans require location, including background location on Android 10/11. `neverForLocation` requires a truthful assertion and can filter beacons. Foreground iOS uses `NSBluetoothAlwaysUsageDescription` and user authorization; ordinary Core Bluetooth does not require MFi participation, as qualified in the [Apple FAQ](https://mfi.apple.com/en/faqs). Background configuration is a separate mode decision, not required for the foreground baseline. Pure BLE does not itself require local-network or contacts access; other features retain their own permissions. [Apple advertising](https://developer.apple.com/documentation/corebluetooth/cbperipheralmanager/startadvertising(_:)) accepts name/service UUIDs with tight payload limits; use GATT for token transfer. [Peer identifiers](https://developer.apple.com/documentation/corebluetooth/cbpeer/identifier) are OS-assigned UUIDs; never use addresses as account identity.

Transport only short-lived pseudonymous meeting/session tokens. Background participation requires explicit timed opt-in, visible status, stop/revoke controls, rotated rendezvous tokens and finite validity; suspended code cannot guarantee timely rotation, so server expiry remains mandatory.

Both parties persist matching nonce-bound receipts and explicit consent locally. Offline actions stay pending. The server authenticates submissions, validates issuer/expiry/revocation and both-party agreement, rejects replay/conflicts, and applies an idempotent final decision. Preissued bounded tokens enable offline candidates; expired tokens require renewed confirmation. BLE proximity/receipts do not prove identity or prevent relay.

## Blockers and validation

Native plugins, permission/entitlement configuration and receipt security remain unimplemented. Use simulators/mocks for bridge/UI/state tests; physical pairs must validate radio roles, first-use and reused permissions, unexpected bonding dialogs, multi-peer targeting, page cleanup, lock/background/restoration, force-stop, Doze, revocation, expiry and asymmetric reconnects. No device result is claimed. Original sources were accessed 2026-10-04; the 2026-10-06 addendum separates current API facts from proposals, including newer background support. Current Core Bluetooth Live Activity text and Google Swift permission keys were directly checked from official page content; they are not hardware evidence.
